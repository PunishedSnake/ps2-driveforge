# MagicGate host implementation

Frieren contains a complete bounded host-side MagicGate capability for the common low-layout PS2 disk KELF path used by the bootstrap pipeline. The implementation deliberately separates structural inspection, cryptographic verification, signing, locally supplied key material and MechaCon-derived ICVPS2 evidence.

The service does **not** own HTTP, filesystem extraction, APA/PFS mutation or raw-disk handles. Providers stage immutable bytes first; the MagicGate service transforms or verifies those staged bytes; the bootstrap planner then consumes only verified output.

## Implemented layers

The host stack is split into independently testable headers:

- `magicgate_cipher.hpp`: DES and two-key TDES primitives;
- `magicgate_cbc.hpp`: bounded CBC helpers;
- `magicgate_kelf.hpp`: KELF structure/layout inspection;
- `magicgate_keyset.hpp`: strict local keyset parser with no compiled Sony secrets;
- `magicgate_disk_keys.hpp`: wrapped disk Kbit/Kc handling;
- `magicgate_signatures.hpp`: header, BIT, content and root signatures;
- `magicgate_content.hpp`: plaintext BIT table and content-signature semantics;
- `magicgate_verify.hpp`: complete low-layout header envelope verification;
- `magicgate_payload.hpp`: content decryption/signature verification plus explicit ICVPS2 evidence checking;
- `magicgate_sign.hpp`: deterministic host signing and independent self-verification;
- `magicgate_service.hpp`: bounded fail-closed capability used by higher-level provider/bootstrap code.

Known-vector and service regression suites run in the dedicated `MagicGate host verification` workflow on Linux and Windows independently from WinUI/Dokany.

## Service boundary

`MagicGateHostService` is the supported high-level entry point. It provides:

```text
inspect(staged KELF)
verify(staged KELF)
sign(immutable sign plan, staged plaintext)
load/revoke local keyset capability
load/revoke ICVPS2 hardware-evidence capability
```

Default bounds are intentionally finite:

```text
keyset text:  64 KiB
KELF:         64 MiB
plaintext:    64 MiB
```

Higher layers may choose stricter limits. They should not silently make them unbounded.

### Inspection

`inspect()` needs no secret material. It proves the bounded KELF geometry, records whether the file requests ICVPS2 and reports which service capabilities are currently loaded.

Structural inspection does not imply cryptographic validity.

### Verification

`verify()` requires a local MagicGate keyset capability and performs:

1. KELF layout validation;
2. low-layout header-signature verification;
3. wrapped Kbit/Kc recovery;
4. BIT table decryption and geometry validation;
5. BIT signature verification;
6. root-signature verification under both public signed-flag interpretations;
7. rejection when the signed/encrypted mapping remains ambiguous;
8. content decryption;
9. per-block content-signature verification;
10. ICVPS2 comparison when the KELF requests it;
11. plaintext size-bound enforcement.

A caller receives plaintext only after every required invariant passes.

### Signing

`sign()` consumes an immutable `DiskKelfSignPlan` and plaintext. It produces the common low-layout disk KELF, then feeds the **exact generated bytes** back through the public service verifier and compares the recovered plaintext byte-for-byte with the source.

Frozen content keys and frozen plans produce deterministic bytes, which keeps fixtures and provider manifests reproducible.

## Local key material

DriveForge intentionally ships no Sony key material.

The strict local keyset format contains ten required capabilities:

```text
MG_SIG_MASTER_KEY
MG_SIG_HASH_KEY
MG_KBIT_MASTER_KEY
MG_KBIT_MATERIAL
MG_KC_MASTER_KEY
MG_KC_MATERIAL
MG_ROOTSIG_MASTER_KEY
MG_ROOTSIG_HASH_KEY
MG_CONTENT_TABLE_IV
MG_CONTENT_IV
```

`MG_KBIT_IV` and `MG_KC_IV` are accepted as compatibility aliases for the corresponding material fields.

Rules:

- every entry is required exactly once;
- unknown names fail parsing;
- malformed hex fails parsing;
- duplicate aliases fail as duplicates;
- file I/O is outside the parser so the caller controls bounded reads and provenance;
- `MagicGateHostService` refuses anonymous keysets and requires a non-empty provenance label;
- key capability revocation performs best-effort in-process byte scrubbing before releasing state.

The synthetic known-vector keyset exists only in tests.

## ICVPS2: hardware evidence, not a guessed software key

KELF header flag bit 1 requests an eight-byte ICVPS2 value stored at `KELF_header_size - 8`.

PS2SDK's MechaCon path obtains ICVPS2 through MechaCon command `0x98` and then stores it in the KELF header. It is not derived by the ordinary public host keyset code.

Frieren therefore models ICVPS2 as a **separate explicit capability**:

```text
local software keyset capability  !=  MechaCon ICVPS2 evidence capability
```

For a KELF that requests ICVPS2:

- verification fails closed when no trusted ICVPS2 evidence is supplied;
- verification compares the embedded eight bytes exactly with the supplied evidence;
- signing fails closed unless the service has explicit ICVPS2 evidence;
- signing stores exactly that evidence in the final eight header bytes;
- the resulting KELF is independently reverified against the same hardware/reference evidence;
- provenance for ICVPS2 is mandatory and retained separately from keyset provenance.

DriveForge does not claim to emulate MechaCon command `0x98` in software when the canonical behavior says the hardware supplies the value.

A future PS2-side helper may acquire ICVPS2 from real MechaCon and export it as a typed evidence record. That acquisition transport is separate from MagicGate cryptography itself.

## Explicit format scope

Code-complete does not mean pretending every Sony KELF layout is one format.

The signer still refuses variable pre-key fields (`flags & 0x0001`) and non-low-layout header-signature modes (`flags & 0xF000`). The verifier likewise requires the low-layout disk header signature currently backed by behavioral vectors.

These are explicit format-scope exclusions rather than missing steps inside the supported low-layout path. Provider strategies must reject unsupported layouts during staging before any write planning begins.

## Security and trust-domain rules

The following invariants are release requirements:

- downloaded/provider bytes are fully staged before MagicGate processing;
- staged bytes have immutable provenance and SHA-256 before signing/verification affects an install plan;
- the MagicGate service cannot obtain a raw-disk writer;
- the bootstrap writer cannot fetch network content;
- secret key material is not logged, serialized into recovery metadata or bundled with releases;
- ICVPS2 provenance is separate from software-key provenance;
- absent, conflicting or ambiguous capabilities fail closed;
- generated KELFs are independently reconsumed before being exposed as verified output.

## Bootstrap integration contract

The automated bootstrap pipeline consumes MagicGate like this:

```text
provider manifest
 -> bounded acquisition
 -> SHA-256 + immutable provenance
 -> host staging / extraction
 -> key-free KELF inspection
 -> local keyset / optional MechaCon ICVPS2 capability acquisition
 -> MagicGate verify or sign
 -> independently verified staged KELF
 -> immutable BootstrapInstallPlan
 -> Rescue Capsule + HDDMBR safety artifacts
 -> guarded image/physical write
 -> cold read-only verification
```

No network object and no MagicGate object receives a `WritablePhysicalDrive`.
