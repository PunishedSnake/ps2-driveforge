# Bootstrap provider and automated installation pipeline

Frieren implements the common host-side pipeline needed to acquire, validate, freeze and install PS2 HDD bootstrap payloads without mixing networking, MagicGate and raw-disk mutation into one trust domain.

Product-specific packaging/filesystem work may still be required for individual FHDB, HDD-OSD, HOSD or PSBBN distributions, but the shared acquisition, cryptographic, immutable-plan and physical-install boundaries are executable code rather than future architecture.

## Non-negotiable rule

**Bytes obtained from the network never flow directly into a writable PS2 device.**

The implemented common path is:

```text
strict local ProviderArtifact manifest
    |
    v
bounded HTTPS acquisition
    |
    v
exact source SHA-256 + immutable provenance
    |
    v
MagicGateHostService inspect / verify / typed sign
    |
    v
exact final payload SHA-256
    |
    v
read-only PhysicalDrive admission + target fingerprint
    |
    v
FrozenInstallInput
    |
    v
pure post-freeze hash / geometry / KELF validation
    |
    v
pre-install PS2HBRC Rescue Capsule
    |
    v
guarded WritablePhysicalDrive lease + HDDMBR
    |
    v
payload write -> flush -> byte verification
    |
    v
osdStart / osdSize pointer publication last
    |
    v
release every RW handle / volume lock
    |
    v
fresh read-only PhysicalDrive master + APA + payload verification
```

A provider never receives a writable block device. The physical installer never performs HTTP requests. `MagicGateHostService` never knows which disk exists. The frozen object between them is the contract.

## Strict provider manifest

`bootstrap_manifest.hpp` implements a bounded strict `key=value` format for local/user-controlled provider descriptions. It rejects unknown keys, duplicates, malformed records and missing required fields.

Required fields are:

```text
provider_id=<stable local/provider identifier>
family=fhdb | hdd-osd | hosd | psbbn | other
version=<already resolved immutable version/tag/build>
asset_url=https://...
asset_name=<expected asset name>
sha256=<exact 64-hex SHA-256>
provenance=<human-readable immutable source evidence>
magicgate=none | inspect | verify | sign
```

Optional:

```text
max_download_bytes=<positive decimal byte limit>
```

The parser itself requires HTTPS, a valid SHA-256 and a MagicGate policy compatible with the selected product family. Named PS2 HDD bootstrap families cannot silently select `magicgate=none`.

No Sony key material, closed bootstrap blob or mutable upstream URL is compiled into DriveForge. This also provides a clean integration route for legally user-supplied HDD-OSD/HOSD/PSBBN inputs.

## Product strategies

`strategy_for()` freezes shared semantics for:

- FHDB;
- HDD-OSD;
- HOSD;
- PSBBN;
- explicit `other` providers.

The four named PS2 families require a KELF-aware policy. HDD-OSD, HOSD and PSBBN are also marked as potentially requiring product-specific filesystem/package staging beyond the common `__mbr` bootstrap payload.

Those flags do **not** create four raw-disk installers. Product-specific code may prepare files or metadata, but it must end at the same common frozen/install boundary.

## Immutable acquisition

`bootstrap::acquire()` refuses a request before transport unless the manifest contains immutable provider/version/provenance identity, HTTPS, an exact SHA-256 and a bounded response limit.

After transport it refuses:

- non-success HTTP responses;
- empty responses;
- responses larger than the frozen limit;
- HTML/XHTML responses masquerading as binary assets;
- any SHA-256 mismatch.

Tests use injected fake HTTP. CI never requires the public internet merely to prove provider safety properties.

A mutable `latest` endpoint may be used by future discovery UI to find a candidate, but it must resolve to immutable version/asset/hash evidence before `bootstrap::acquire()` and long before a physical write lease.

## MagicGate boundary

`MagicGateHostService` separates:

```text
inspect
verify
sign
local software keyset capability
MechaCon ICVPS2 evidence capability
```

DriveForge ships no Sony secrets. Local keysets are bounded, strictly parsed, provenance-labelled and revocable.

PS2SDK obtains ICVPS2 from MechaCon command `0x98`, so DriveForge does not pretend that an unknown hardware-derived value can be reconstructed by optimism. KELFs requiring ICVPS2 consume explicit eight-byte hardware/reference evidence and fail closed when it is absent or mismatched.

Host signing is deterministic when its typed inputs are frozen and the exact generated bytes are independently reconsumed by the verifier before success is returned.

The generic WinUI provider surface currently accepts `inspect` and `verify` paths for existing KELFs. `magicgate=sign` remains fail-closed in generic manifests until a typed product strategy supplies the complete `DiskKelfSignPlan`; the UI does not infer signing flags, content keys or block geometry from a filename. The signer itself is implemented and tested independently.

See [`magicgate-host.md`](magicgate-host.md).

## Prepared and frozen inputs

`bootstrap::prepare()` converts an acquired artifact into one explicit prepared payload and records:

- source SHA-256;
- final payload bytes;
- final payload SHA-256;
- whether MagicGate inspection, verification or signing occurred.

`bootstrap::freeze_install_input()` then freezes:

- product family;
- provider ID;
- immutable version;
- provenance;
- source SHA-256;
- final payload SHA-256;
- exact final bytes;
- canonical `__mbr` program start;
- exact 512-byte sector count;
- target media fingerprint captured through read-only physical admission.

`validate_frozen_payload()` is pure and cross-platform. It rechecks the final hash, target identity presence, canonical program start, exact sector geometry, payload size limit and KELF structure/trailing-byte condition for named PS2 strategies.

Changing one byte, one sector count or the target identity after preview therefore invalidates the object before target-specific write admission.

## Guarded physical install

`install_bootstrap_to_physical()` consumes only a valid `FrozenInstallInput` plus a host-side safety directory.

Its order is:

1. open ordinary `PhysicalDrive` read-only;
2. require normal clean physical-write authorization;
3. compare the live media fingerprint to the frozen target fingerprint;
4. revalidate frozen payload/hash/KELF geometry;
5. read and validate the live APA master;
6. capture a canonical pre-install Rescue Capsule read-only;
7. persist that `HDDRESCUE` evidence;
8. obtain `WritablePhysicalDrive` with the already frozen authorization and Windows volume locks;
9. reuse `apply_bootstrap_restore()` rather than inventing another sector writer;
10. persist mandatory current-master `HDDMBR` before-image;
11. write and read back the complete padded payload first;
12. publish only `osdStart` / `osdSize` plus APA checksum last;
13. close the RW lease and volume locks;
14. reopen a fresh read-only `PhysicalDrive`;
15. verify master identity/pointer, clean APA scan and exact payload bytes.

A corrupt live bootstrap pointer blocks normal provider installation because the pre-install Rescue Capsule cannot truthfully represent valid historical evidence. That target belongs in the recovery workflow first.

## WinUI provider surface

HDL Tools exposes the common provider pipeline without launching a developer CLI.

The user selects:

- a local provider manifest;
- a local MagicGate keyset when the policy requires verification;
- optional ICVPS2 evidence and an explicit provenance label;
- the existing safety/recovery artifact directory.

**Stage and verify provider** runs asynchronously and performs all network, hashing, MagicGate and read-only target fingerprint work. It displays product/version, provider ID, source SHA-256, final payload SHA-256, payload bytes/sectors and target fingerprint.

Only that frozen preview can enable **Install frozen provider**. Physical commit then uses the same literal `PhysicalDriveN` confirmation mechanism as the rest of Frieren's GUI writes.

The endpoint still rechecks the live fingerprint, so swapping disks after preview is a refusal rather than an exciting new feature.

## Recovery artifacts remain separate

A bootstrap install may create both:

- `PS2HBRC` Rescue Capsule, interoperable historical/bootstrap evidence shared with FHDB Manager;
- `HDDMBR`, exact current-master before-image used by bootstrap recovery;
- DriveForge `PS2DFRC1` Mutation Journal where the specific storage transaction uses it.

They are not aliases and do not share trust semantics merely because all three are useful after something unpleasant happens.

## Product-specific integration boundary

FHDB, HDD-OSD, HOSD and PSBBN remain separate product strategies over the shared provider/install path.

A strategy may decide:

- which immutable artifacts are required;
- whether an archive/container must be extracted;
- which KELF is selected;
- whether a typed MagicGate sign plan is required;
- whether product-specific PFS files/directories must be staged;
- which HDD-OSD metadata is produced;
- which final product-specific evidence proves success.

A strategy may not decide:

- to skip HTTPS/hash/provenance checks;
- to replace a missing keyset or ICVPS2 with guessed constants;
- to silently change the frozen target disk;
- to ignore GPT/APA admission policy;
- to skip Rescue/HDDMBR before-images;
- to publish a bootstrap pointer before payload readback;
- to treat failed cold verification as success.

## CI and release boundary

The standalone cross-platform workflow is now **MagicGate and bootstrap provider host verification**. It exercises MagicGate vectors, host service behavior, provider acquisition, strict manifest parsing and frozen-input tamper/refusal cases on Linux and Windows.

This does not graduate physical mutation by itself. Frieren still needs representative real KELFs/ICVPS2 evidence, legally usable pinned provider fixtures and the destructive sacrificial-HDD checklist before a built-in product strategy can be advertised as release-ready.

CI can prove deterministic software invariants. It cannot volunteer GitHub's runner disk as a sacrificial PS2 HDD, despite how convenient that would be.
